# DIY-Dungeon 开发工作流

> 本文档面向 AI Agent 和开发者，描述每次功能开发的标准流程。
> **强制执行**：所有新功能开发必须严格按此流程进行，不得跳过任何步骤。

---

## 概览

```
读文档 → 比对代码 → 出计划 → 确认 → 开发 → 构建/测试 → 更新文档
```

---

## Step 1：确认必读文档

在开始任何开发前，**向用户确认**本次需要阅读哪些文档：

**必读（每次都要读，每次都会更新）**：
- `docs/GAME_DESIGN.md` — 游戏设计全景，含境界/战斗/沙盒/人物/待开发清单
- `docs/ARCHITECTURE.md` — 项目结构/模块职责/关键注意事项/待扩展模块

**按功能选读**：
- `docs/TODO_LIST.md` — 开发待办清单（做沙盒类功能时必读，了解哪些已完成哪些待做）
- `docs/REALM_SKILL_FABAO_SYSTEM.md` — 境界/技能/法宝体系（改技能/法宝时必读）
- `docs/chapters/CHAPTER*.md` — 对应章节剧本（改剧情时必读）

**确认话术示例**：
> 本次开发前我需要读以下文档：`GAME_DESIGN.md`、`ARCHITECTURE.md`、`TODO_LIST.md`。
> 确认后我开始阅读。还有其他需要参考的文档吗？

---

## Step 2：阅读文档，识别待完成内容

阅读完文档后，重点关注：

1. **`GAME_DESIGN.md` §十一·待完成** — 当前未完成的功能清单
2. **`ARCHITECTURE.md` §十·待扩展模块** — 各阶段完成状态（✅ / 🔄 / 🔜）
3. **`TODO_LIST.md` 待办清单** — 各功能完成状态 + 剩余待办项

**比对现有代码**：针对文档中标注为"待完成"或"🔜"的内容，在代码库中验证：
- 对应文件是否已存在？
- 关键函数/接口是否已实现？
- 类型定义是否已在 `src/data/types.ts` 声明？

```
文档说"待完成" ≠ 代码里真的没有
文档说"已完成" ≠ 代码里真的有且正确
→ 必须读代码验证，不能只信文档
```

---

## Step 3：制定实施计划

基于 Step 2 的比对结果，制定本次开发计划：

**计划内容应包含**：
1. **目标**：本次要实现什么功能，解决什么问题
2. **涉及文件清单**：列出所有需要新建/修改的文件，说明改动内容
3. **实施批次**（如果工作量大）：拆分为可独立验证的小批次
4. **类型变更**：是否需要修改 `types.ts`、`schemas.ts`（影响存档兼容性）
5. **已知风险**：可能影响现有功能的地方

**格式参考**：

```
## 本次计划：[功能名称]

### 目标
[1-2句话描述]

### 涉及文件
| 文件 | 类型 | 改动说明 |
|------|------|---------|
| src/data/types.ts | 修改 | 新增 XxxId 联合类型 |
| src/systems/XxxSystem.ts | 新建 | 实现核心逻辑 |
| src/screens/camp/XxxPanel.ts | 修改 | 新增UI入口 |

### 实施步骤
1. 更新类型定义
2. 实现系统逻辑
3. 接入UI
4. 测试验证
```

---

## Step 4：与用户确认计划

将 Step 3 的计划完整呈现给用户，**等待明确确认后再开始编码**。

确认要点：
- 功能范围是否正确
- 文件改动是否有遗漏或超出预期
- 是否有特殊限制（如不改某文件、不影响某功能）

> ⚠️ **不得在未获确认前开始修改任何文件**

---

## Step 5：按计划开发

遵循项目编码规范：

### TypeScript 类型安全
- 新增游戏数据 ID **必须先在 `src/data/types.ts` 的联合类型中声明**，再在其他文件使用
- `tsc --noEmit` 零报错才算完成
- 修改 `PlayerState` **必须同步更新 `src/state/schemas.ts`**，新字段必须有 `.default()`

### 沙盒地基原则
- 新功能应构建在沙盒底层之上
- 剧情代码可以直接设置玩家字段（作弊层），但核心循环必须通过沙盒机制推进
- 不要修改 `src/data/chapters/ch1.ts`～`ch3.ts` 和 `src/data/npcs.ts` 中的主线剧情内容

### 代码规范
- 不创建过度抽象，不为假想的未来需求设计
- 不加不必要的注释，不写记录"这次改了什么"的注释
- 修改现有文件优先于创建新文件

---

## Step 6：构建与测试

开发完成后执行构建验证：

```powershell
# Windows 环境使用 PowerShell 工具
npm run build
# 或
npx tsc --noEmit   # 只做类型检查，更快
```

**验证清单**：
- [ ] `tsc --noEmit` 零 TypeScript 错误
- [ ] `npm run build` 构建成功，无报错
- [ ] 核心功能路径可正常运行（在浏览器中手动验证）
- [ ] 旧存档加载不崩溃（如有新的 `PlayerState` 字段）
- [ ] 不影响已有功能（战斗/营地/地图等核心循环）

**如有 bug**：修复后重新执行验证，直到全部通过。

---

## Step 7：更新文档

开发测试全部通过后，**必须更新**本次开发前阅读的所有文档：

### `docs/GAME_DESIGN.md`
- **§十一·待完成** → 将已完成的项目移至 **§十一·已完成** 或标注 ✅
- 如果新功能改变了设计，更新对应设计章节（如新增行动、修改境界规则等）

### `docs/ARCHITECTURE.md`
- **文件结构树**（§二）→ 新增/修改的文件补充进去
- **模块职责**（§三）→ 新建模块需添加说明，修改的模块需更新描述
- **关键注意事项**（§九）→ 添加本次引入的新机制/注意点（编号续接）
- **待扩展模块**（§十）→ 已完成的标注 ✅，新增的待开发项写入
- 顶部 `最后更新` 日期和摘要更新

### `docs/TODO_LIST.md`（每次开发后必更新）
- **待完成** → 新增的功能在此登记，完成后勾选 ✅
- **当前开发状态** → 更新已完成/进行中/下一步
- **已完成方向速览** → 标注 ✅ 并更新说明

### 文档更新原则
- **只记录"为什么"和"是什么"，不记录"这次做了什么"**（git history 负责记录过程）
- 更新后文档应能让一个全新的 AI 读完就能准确理解当前代码状态
- 如果某个"待完成"的功能现在已完成，删掉"计划"描述，换成"已实现"描述

## 快速参考

### 常见改动的文件路径

| 改动类型 | 必改文件 | 可能影响 |
|---------|---------|---------|
| 新增技能 | `types.ts`（SkillId）、`skills.ts`、`sectSkillTables.ts` | `NpcBehavior.ts` |
| 新增地点 | `types.ts`（LocationId）、`worldMap.ts`、`Camp.ts`（POS） | `NPCGenerator.ts` |
| 新增任务 | `sandboxTypes.ts`（MissionDef）、`MissionSystem.ts` | `StoryPanel.ts` |
| 新增 PlayerState 字段 | `types.ts`、`schemas.ts`（Zod .default()） | `SaveSystem.ts` |
| 新增屏幕/面板 | `types.ts`（ScreenId/CampTabId）、`index.html`、对应 `.ts` | `Camp.ts` |
| 新增敌人 | `types.ts`（EnemyId）、`enemies.ts` | `BattleEngine.ts` |

### Windows 环境注意
- Shell 命令用 **PowerShell 工具**，不用 Bash 工具
- 路径分隔符在 TypeScript 代码中用正斜杠 `/`
